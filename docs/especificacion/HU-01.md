# HU-01. Aplicación conectada y arquitectura base

Paso 44.

## Historia

Como miembro del equipo de mantenimiento, quiero abrir la aplicación y que esté conectada al sistema, para trabajar con los datos reales de las plantas.

## Criterios de aceptación

1. El `manifest.json` declara el origen de datos `mainService` y el modelo por defecto OData V4 con los ajustes de `docs/arquitectura.md`, y las librerías `sap.f`, `sap.uxap`, `sap.ui.layout` y `sap.ui.unified`.
2. `App.view.xml` contiene un `sap.f.FlexibleColumnLayout` con id `fcl`, cuya disposición está ligada a la propiedad `layout` del modelo `appView`.
3. El enrutador es `sap.f.routing.Router`, con las rutas `list` y `detail` de `docs/arquitectura.md`.
4. Existen las vistas `RequestList` y `RequestDetail` con sus controladores, cada una con su título desde `i18n` y sin contenido funcional todavía.
5. Existe `controller/BaseController.ts` con acceso tipado al enrutador, a los modelos, a los textos y al modelo `appView`. Todos los controladores lo extienden.
6. `Component.ts` crea los modelos `device` y `appView`, inicializa el enrutador y crea y destruye el gestor de errores.
7. `controller/ErrorHandler.ts` muestra un único cuadro de mensaje cuando el servicio devuelve un error técnico (sin conexión, 401, 403, 500), sin duplicarlo.
8. La aplicación arranca sin errores de consola contra el servicio real y contra el servidor simulado, y pide los metadatos una sola vez.
9. Todos los textos están en `i18n.properties` y en `i18n_es.properties`.

## Notas técnicas

- El modelo OData V4 no ofrece operaciones imperativas de lectura: los datos se piden a través de bindings. Con `autoExpandSelect`, el modelo calcula `$select` y `$expand` a partir de lo que usan las vistas.
- Los errores llegan como mensajes al modelo de mensajes (`sap/ui/core/Messaging`). Los técnicos se distinguen de los de validación; confirmar con la API cómo.
- El patrón de gestor de errores habitual en las aplicaciones con el modelo OData V2 sirve de referencia, pero sus eventos son del modelo V2 y no existen en V4.
- El bloque `dataSources` y el bloque `models` del `manifest.json`, la tabla de rutas y los modelos auxiliares están fijados en `docs/arquitectura.md`, apartado 5.
- El servidor simulado se arranca con `npm run start-mock` o `npm run start-mock-noflp` y se configura en `ui5-mock.yaml` (`docs/arquitectura.md`, apartado 7).
